# C-Transit Backend — Card, Driver Terminal, Kora & Payment Contracts

## Overview
This document specifies the authoritative contracts, architectural flows, and hardware boundary expectations implemented for:
1. Driver Physical Card Linking (via 6-digit terminal OTP)
2. Driver Terminal Card PIN Provisioning (bcrypt hash, terminal downlink)
3. Driver Terminal State Contract (`terminalId`, `terminalStatus`, `terminal` object)
4. Authority Card Unlinking (Admin & Agent only, cross-role: student, driver, agent, admin)
5. Driver Bank Account Verification (Kora resolution) & Withdrawal Flow (server-verified name enforcement)
6. Hardware Downlink & Provisioning Boundary (`TerminalProvisioningService`)

---

## 1. Driver Physical Card Linking

### Architecture & Security Guarantees
- **No Client-Dictated Card UID:** The client does NOT supply `cardUid` to choose the card. The card UID is resolved strictly server-side from the verified `RegistrationOtp` record generated by the terminal tap.
- **Server-Side Driver Identity:** The driver identity is derived entirely from the authenticated session (`req.user.userId`). Client-supplied `driverId` is strictly validated against the token and rejected if mismatched.
- **Single-Card Invariant:** A driver can only have one active card linked at a time. If an existing card is linked, the driver must have it unlinked before linking another (`DRIVER_ALREADY_HAS_CARD`).
- **No Silent Card Reassignment:** If a card is already linked to another user, linking is rejected with HTTP 409 (`CARD_ALREADY_LINKED`).
- **Atomic OTP Consumption:** Uses a Prisma atomic transaction to prevent race conditions or duplicate claiming (`OTP_ALREADY_USED`).
- **Terminal Whitelist Provisioning:** Upon successful link, `TerminalProvisioningService` delivers `ADD:WL,<cardUid>` to the origin terminal queue and broadcasts across the fleet.

### Endpoint: `POST /api/drivers/card/link`
- **Auth:** Bearer JWT (`DRIVER` role)
- **Rate Limit:** 10 requests / 15 min

#### Request Body
```json
{
  "otp": "492817"
}
```
*(Optional sanity parameters `cardUid` or `driverId` may be provided, but if they conflict with the authenticated driver or the OTP record, the request is rejected).*

#### Success Response (200 OK)
```json
{
  "success": true,
  "message": "Driver card linked successfully",
  "cardUid": "A1B2C3D4",
  "driverId": "DRV-2026-001"
}
```

#### Error Codes
- `400 INVALID_OTP_FORMAT`: OTP must be exactly 6 numeric digits.
- `400 INVALID_OTP`: OTP record not found.
- `400 OTP_EXPIRED`: OTP has passed its 5-minute validity window.
- `400 OTP_ALREADY_USED`: OTP was already claimed.
- `400 DRIVER_ALREADY_HAS_CARD`: Driver already has an active linked card.
- `400 CARD_MISMATCH`: Client-provided `cardUid` differs from OTP record.
- `403 UNAUTHORIZED_DRIVER_ID`: Client-provided `driverId` differs from authenticated driver.
- `409 CARD_ALREADY_LINKED`: Physical card is linked to another user.

## 2. Driver Card PIN (Physical Terminal Authentication)

### Lifecycle & Security Guarantees
- The PIN is strictly for physical C-Transit hardware terminal login (driver taps card on bus terminal, then inputs PIN).
- The PIN is NEVER stored in plaintext. It is hashed using `bcrypt` (work factor 10) and stored in the dedicated `DriverCardCredential` model.
- The PIN and hash are NEVER returned to the frontend, NEVER included in logs, and NEVER exposed in API responses.
- The driver MUST have an active linked card before a PIN can be set.

### Endpoint: `POST /api/drivers/card/pin`
- **Auth:** Bearer JWT (`DRIVER` role)
- **Rate Limit:** 10 attempts / 15 min (`driverPinLimiter`)

#### Request Body
```json
{
  "pin": "1234"
}
```
*Constraints: 4 to 6 numeric digits (`/^\d{4,6}$/`).*

#### Success Response (200 OK)
```json
{
  "success": true,
  "message": "Terminal PIN set successfully",
  "cardUid": "A1B2C3D4"
}
```

### Endpoint: `GET /api/drivers/card/pin/status`
- **Auth:** Bearer JWT (`DRIVER` role)

#### Success Response (200 OK)
```json
{
  "success": true,
  "isCardLinked": true,
  "cardUid": "A1B2C3D4",
  "hasPin": true
}
```

## 3. Driver ↔ Terminal State

### Overview
Terminals track the currently active driver via `Terminal.active_driver_uid`.
When a driver logs into a terminal (`handleDriverLogin`):
1. Any other terminal where this driver was previously active is cleared (single-terminal invariant).
2. The current terminal sets `active_driver_uid = driver.matricNumber`.

When a driver logs out (`handleDriverLogout`):
`active_driver_uid` is cleared to `null`.

### Endpoint: `GET /api/drivers/dashboard`
- **Auth:** Bearer JWT (`DRIVER` role)

#### Response when Driver is logged into a terminal:
```json
{
  "todayEarnings": 12500.00,
  "todayRidesCount": 18,
  "availableBalance": 45200.50,
  "terminalId": "TERM_BUS_04",
  "terminalStatus": "ONLINE",

```

#### Response when Driver is NOT logged into any terminal:

{
  "todayEarnings": 0,

## 4. Authority Card Unlinking (Admin & Agent Only)

### Security & Invariants
- Regular users (students/drivers) CANNOT unlink cards. Only `ADMIN` and `AGENT` roles are authorized.
- Can be invoked by `cardUid` OR by `userIdentifier` (matricNumber, email, or user ID).
- Financial ledger records (`Transaction`, `Wallet`, `DriverWallet`, `Withdrawal`) are strictly PRESERVED for auditing and accounting integrity.
- Removes:
  1. `CardMapping`
  2. `DriverCardCredential` (if applicable)
- Clears Redis read-through hot cache (`card:map:<cardUid>`).
- Enqueues `DEL:WL,<cardUid>` downlink command to origin terminal and fleet broadcast.

### Endpoints
- `POST /api/admin/card/unlink` (Admin only)
- `POST /api/agents/card/unlink` (Agent or Admin)

#### Request Body
```json
{
  "cardUid": "A1B2C3D4"
}
```
*or*
```json
{
  "userIdentifier": "DRV-2026-001"
}
```

#### Response (200 OK)
```json
{
  "success": true,
  "message": "Card successfully unlinked",
  "cardUid": "A1B2C3D4",
  "unlinkedFrom": "DRV-2026-001",
  "unlinkedRole": "DRIVER",
  "terminalSync": {
    "success": true,
    "deprovisioned": true
  }
}
```

## 5. Driver Bank Verification & Withdrawal Contracts

### Bank Account Verification: `POST /api/drivers/bank/verify`
- Resolves account name dynamically against Kora payment provider (`/merchant/api/v1/charges/bank/resolve`).
- Persists `bankCode`, `bankName`, `accountNumber`, `accountName`, and `bankVerified = true` on the `User` model.
- Rate limited: 15 requests / 15 min.

#### Request Body
```json
{
  "bankCode": "044",
  "accountNumber": "0123456789"
}
```

#### Response (200 OK)
```json
{
  "success": true,
  "message": "Bank account verified successfully",
  "data": {
    "bankCode": "044",
    "bankName": "Access Bank",
    "accountNumber": "0123456789",
    "accountName": "JOHN DOE",
    "bankVerified": true
  }
}
```

### Driver Withdrawal Initiation: `POST /api/drivers/withdraw`
- **Strict Verification Enforcement:** Rejects if `driver.bankVerified !== true` (`BANK_NOT_VERIFIED`).
- **No Client Account Name Override:** Account name is strictly sourced from server-persisted verified name, preventing fraud.
- **C-Transit Fee:** Driver bears a 4% payout fee (`fee = 0.04 * grossAmount`).

## 6. Hardware Team Downlink Protocol Boundary

### Current State
1. **Card Whitelist Add:** `ADD:WL,<cardUid>` (enqueued to origin terminal, broadcast to fleet).
2. **Card Whitelist Remove:** `DEL:WL,<cardUid>` (enqueued to origin terminal, broadcast to fleet).
3. **Driver Card + PIN Downlink Protocol:**
   - Isolated in `TerminalProvisioningService.provisionDriverPin({ cardUid, driverUid })`.
   - **PENDING HARDWARE TEAM SPECIFICATION:** The exact downlink command format for transmitting encrypted/hashed PIN or credential payloads to physical terminals will be provided by the hardware engineering team.
   - The backend domain logic, bcrypt hashing, database persistence, and service abstraction are complete and ready to integrate the exact wire format once provided.
